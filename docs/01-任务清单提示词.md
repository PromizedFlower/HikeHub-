# 产品定位

一句话：把散落在论坛与 Facebook 群组的香港行山资讯，结构化成一条条可浏览、可打卡、
可发问的路線。

产品形态参考「两步路」的骨架——路线库 + 打卡 + 社区，但走**极简路线**。
两步路今天的内容密度是反面教材：商城、活动报名、领队认证、会员积分、资讯流、
话题广场、达人榜、付费路书，全是与我们无关的重量。我们只保留一条主干：

**找路线 → 出发行山 → 留下打卡 → 发到社区 → 被别人看到并互动**

这条闭环就是课程评分里"实用性"的落点。任何功能如果不能落在这条链上，就不要加。

**产品重心是社交，不是工具。** 我们不是做一个纯记录里程的行山工具，而是做一个
「走完有人看、有人赞、有人问」的行山社区。所以取舍时的优先级是：

**社区互动 > 路线库丰富度 > 其他一切**

具体表现：动态的点赞/评论/收藏要做得顺滑、有即时反馈；发布流程要短（选图 → 一句话 → 发）；
社区要有"这条路线最近有人走过"的活人感（首页热帖、路线详情里挂相关动态）。

**不做任何商业化功能。** 没有商城、没有订单、没有支付、没有会员、没有广告、
没有付费路书。这是产品定位决定，不是工期妥协 —— 加进来会稀释社交体验。

## 每个 Tab 的内容边界（照此实现，不要自行扩充）

**1 首页 HomePage**
- 顶部搜索框（路线名 / 地区关键字）
- 「进行中的行山」卡片（仅在有未结束会话时出现）
- 「本周精选」2 张横向大卡
- 「附近路线」横向滑动列表
- 「社区热帖」3 条（按点赞数取）
- 不做：无限流、资讯、运营 banner、广告位、每日签到

**2 线路 RouteListPage**
- 顶部筛选 chip：地区 / 难度 / 时长
- 卡片：封面图、路线名、难度徽章、距离、爬升、收藏数
- 不做：地图预览、海拔曲线、天气、付费路书

**3 出发 StartPage（地图 + 轨迹，三态）**

产品逻辑与两步路一致：选一条路线 → 地图上看路线 → 开始记录 → 沿途打卡 → 结束生成记录 → 发布到社区。

- 未开始：地图铺满，显示已选路线的折线与打卡点标记；底部卡片「选择路线 / 开始出发」
- 行山中：地图实时跟随当前位置，走过的部分画成实线、未走部分虚线；顶部三个数字
  （距离 km / 时长 / 已打卡 n/m）；底部「打卡」「拍照」「结束」
- 结束：结算卡（路线、距离、时长、打卡点数、照片张数、爬升）→「发布到社区」/「仅保存」

**定位双源设计（这是关键，不要只写一种）**：
- `LocationProvider` 抽象出「当前位置」接口，两个实现：
  - `SystemProvider`：QtPositioning 的 `PositionSource`（Windows 走 winrt 插件）
  - `SimulatedProvider`：沿路线折线按时间插值推进的假坐标
- 启动时先试系统定位；3 秒内拿不到有效坐标，自动切模拟源，并在界面顶部显示
  「示範模式 · 模擬定位」小标签，不弹窗、不报错
- **这是为 Demo 服务的**：教室和办公室里通常没有 GPS 信号，真实定位大概率失败。
  模拟源保证演示可复现，且轨迹形状真实

**地图技术选型**：QML 的 `Map` + `Plugin { name: "osm" }`，`MapPolyline` 画轨迹、
`MapCircle` 标打卡点。OSM 瓦片免 key、免注册，覆盖香港良好。

**不做**：离线地图包、自建瓦片服务器、路线导航语音播报、实时天气图层。

**4 社区 CommunityPage**
- 顶部 segment 切换：动态 / 问答
- 动态流：双列瀑布流图片卡（封面图、一句话正文、作者头像+昵称、点赞数、收藏数）
- 问答列表：标题、标签（装备/交通/天气）、回答数、是否已采纳
- 右上「+」→ ComposePage
- 排序：纯时间倒序

**5 我的 ProfilePage**
- 头像 + 昵称 + 一句话简介
- 三个数字：动态数 / 收藏数 / 行山次数
- 「我的动态」网格（可进详情，可编辑/删除）
- 「我的收藏」两个子 tab：收藏的路线 / 收藏的动态
- 设置区：编辑资料、登出

## 社区互动规格（本次重点，必须精确）

| 互动 | 规则 | 数据落点 |
|---|---|---|
| 点赞 | 单一 like，可取消；同一用户对同一条内容只能有一条 | likes，PK(post_id, user_id) |
| 收藏 | 单一收藏，可取消；收藏后出现在「我的-收藏」 | favorites，target_type ∈ {trail, post} |
| 评论 | 一级评论 + 一层回复（回复只显示 @昵称），不做无限嵌套 | comments，parent_id 为空即一级 |
| 采纳 | 仅问答类型有；作者可采纳一条回答，采纳后不可撤销 | comments.is_accepted |
| 计数 | 列表页显示点赞/评论/收藏数，点击后立即更新 | posts 冗余计数字段，trigger 维护 |

**社区不做**：转发、私信、关注、话题聚合页、@提醒、消息通知、举报、内容审核后台。
理由：都要额外一套后台与状态机，六周做不完，且不加分。

# 实现路径：我们怎么把这个东西做出来

## 一、四层结构（自上而下，只允许单向依赖）

```
L1  视图层    app/pages/*.qml + components/*.qml     只画界面、只发信号
L2  桥接层    app/backend/bridge.py                   QObject，把 service 包成 QML 能调的
                                                      方法与 Signal
L3  服务层    app/backend/*_service.py                唯一碰数据的地方
L4  数据层    Supabase（Postgres + Auth + Storage）    托管，不自建后端
```

依赖只能向下，不能反向：**页面不知道 SQL 存在，service 不知道 QML 存在**。

## 二、一次请求的完整形状（以"点赞"为例，所有功能照此写）

```
用户点爱心（QML）
  → api.toggleLike(postId)            [bridge.py，QML 只认这个方法名]
  → social_service.toggle_like()      [服务层，校验 + 组 SQL]
  → supabase-py 发请求
  → Postgres 执行 + RLS 校验权限
  → 写 likes 表 → trigger 更新 posts.like_count
  → 返回新计数 → bridge 发 Signal → QML 更新数字
```

每个功能都长这个样子。写代码前先确认这五段分别落在哪个文件，
缺哪一段就说明设计没想清楚，不要动手。

## 三、从零到 Demo 的纵向顺序（不能跳步）

1. 环境验针（6 支纯 Python / 纯 QML 脚本，不写任何业务 UI）：
   ① PySide6 起窗口 ② Supabase 登录 ③ 建表读写 ④ Storage 上传并显示
   ⑤ **地图出图**（QML Map + OSM 插件，能看到香港地图） ⑥ **定位出坐标**
   （PositionSource 能拿到 lat/lng，或确认必须走模拟源）
2. schema.sql + seed.sql 落地 → Supabase 后台能看到 9 张表与种子数据
3. service 签名冻结（G1）→ 先返回假数据，C / D 即刻可开工
4. App 壳 + BottomTabBar + 登录（B）
5. 元件库冻结（G2）
6. 三条线并行填页面（C 线路+出发+地图 / D 社区+我的 / A 补 service 实现）
7. 串接、打磨、截图
8. PyInstaller 打包 exe + 报告 + Demo

第 2 步做完之前不要写任何页面。第 ⑤ ⑥ 支验针做完之前，不要写「出发」页面的任何代码。

## 四、交付与运行

开发期 README 三步：`pip install -r requirements.txt` → 填 `.env` → `python main.py`。
交付期：`HikeHub.exe` 双击即跑。

**Key 管理**：

| 变量 | 放哪 | 说明 |
|---|---|---|
| `SUPABASE_URL` | `.env.example`，**提交到 repo** | 助教必须拿得到 |
| `SUPABASE_ANON_KEY` | `.env.example`，**提交到 repo** | 本来就设计给前端公开，安全靠 RLS |
| `SUPABASE_SERVICE_ROLE_KEY` | **永不进 repo、永不进 .env.example** | 只在 A 本地跑 seed 时临时用 |

原文档"絕不把 key 提交到 repo"应修正为"**絕不把 service_role key 提交**"。
anon key 藏着不提交，代价是助教跑不起来。

**打包 exe 的具体要求（W6 任务）**：

- 用 PyInstaller，`--windowed`，QML 目录必须 `--add-data "app;app"`，漏了就是运行时白屏
- `.env` 从 exe 同目录读取，不打包进 exe 内部（方便换环境）
- 体积 60–100MB 属正常（PySide6 自带 Qt 运行时），不要为此做裁剪
- 验收标准：**在一台没装 Python 的 Windows 机器上双击 exe，能登录、能看到路线列表**
- 打包失败是环境问题，不要为它改架构、降级功能

**首次启动的兜底**：连不上 Supabase 时，登录页要显示"检查 .env 配置"的明确提示，
不能白屏、不能抛未捕获异常。这条要写进验收标准。

# 技术栈（硬约束）

- Python 3.11+，PySide6 == 6.9.x，Qt Quick / QML
- 数据：Supabase（Postgres + Auth + Storage），经 supabase-py 访问
- 打包：PyInstaller
- 不引入文档外的框架：不用 Flask / Django / FastAPI，不用 React / Vue，不用 tkinter
- 界面全繁體中文，用词港味：行山、路段、補給點、撤退點、打卡、湊人、山友

## 四条不可违反的架构约定

1. QML 只负责画面与交互，不写任何 SQL，不直接调 supabase-py
2. 所有数据访问只能经过 backend/*_service.py，页面逻辑不碰数据库
3. service 层统一返回 dict / list[dict]，字段名与数据库列名一致
4. 所有网络请求放 QThread / QThreadPool，用 Signal 回传，绝不冻结 UI

## 导航实现约定（B 必须照此搭，否则后面所有人返工）

- `main.qml` = ApplicationWindow + Column：上方 `StackView`（内容区），下方 `BottomTabBar`
- **每个 Tab 各自持有一个 StackView**，子页在该 Tab 内 push，切换 Tab 不丢各自栈

## 数据契约状态

9 张表的 schema 尚未冻结，由 A 在 W1 定稿。参考基线（最终以 schema.sql 为准）：

1. `profiles` — id(=auth.uid), nickname, bio, avatar_url, created_at
2. `trails` — id, name, region, difficulty, distance_km, ascent_m, duration_min, cover_url,
   description, **path(jsonb)** — 折线坐标 `[[lat,lng],...]`，地图画路线用
3. `trail_segments` — id, trail_id, seq, name, distance_km, ascent_m, has_supply, has_retreat, note
4. `checkpoints` — id, trail_id, segment_id, seq, name, **lat, lng**, note
5. `posts` — id, author_id, type(moment|question|trip), title, body, trail_id,
   **meta(jsonb)** — trip 类型存 `{distance_km, duration_sec, ascent_m, path:[[lat,lng],...]}`,
   like_count, comment_count, favorite_count, created_at
6. `post_photos` — id, post_id, storage_path, seq
7. `comments` — id, post_id, author_id, parent_id, body, is_accepted, created_at
8. `likes` — post_id, user_id, created_at（PK 复合）
9. `favorites` — user_id, target_type(trail|post), target_id, created_at

设计要点：**动态、问答、行山记录是同一张 posts 表，靠 type 区分**；
问答的「回答」就是 comments，采纳就是 comments.is_accepted；
行山记录的轨迹与统计塞进 `posts.meta`，不额外建表。
这样 9 张表装下全部功能，社区与问答共用一套详情页与发布页。
不得自行发明表名或字段；涉及数据的任务统一写「按 schema.sql 冻结版」。

## 技术风险（已识别，任务清单里要有应对任务）

- **地图瓦片加载不出来（白底/灰块）** —— 概率中，最高优先级。QtLocation 的 OSM 插件走网络，
  国内网络对 tile.openstreetmap.org 可能慢或被拦；Step 0 就要验证能否出图，
  出不来立刻换 MapLibre 插件或加瓦片缓存
- **Qt 6.9 与 6.12 的地图 API 差异** —— 概率中。本机装的是 PySide6 6.12，其中 QtLocation
  已出现新的 `MapView` 类型；6.9 是否有、API 是否一致，必须在 6.9 上验一次，
  不要照着 6.12 写完才发现跑不了
- **桌面端拿不到真实定位** —— 概率高。Windows 走 winrt 插件，台式机通常无定位硬件。
  已用双源设计兜底（3 秒无坐标切模拟），但模拟源必须在 W2 就写出来，不能拖
- Storage 上传链路不通（选档 / bytes / 上传 / 显示）—— 概率高，Step 0 就要验
- QML Image 显示不了 Supabase 图片 —— 中，bucket 设 public 或改用 signed URL
- 网络请求冻结 UI —— 高，全部走 QThread
- RLS 政策写错读不到数据 —— 中，开发期先开宽松 read，收尾再收紧
- 底部 Tab + 每 Tab 独立 StackView 的返回键行为不一致 —— 中，B 在 W2 就定死规则
- PyInstaller 打包后 QML 找不到、地图插件缺失 —— 中，build.spec 要显式带 qml 与 plugins，
  W6 第一件事就验
- 四人进度落差 —— 中，W3 末做检查点，落后者缩范围而不是硬撑
